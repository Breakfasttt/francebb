module : interface + implémentation profond : beaucoup de comportement derrière peu d'interface superficiel : interface presque aussi grosse que le code seam : là où vit l'interface rouge : fuite / copie divergente
Constat transversal : les tests unitaires (node --test) ne résolvent pas l'alias @/. Seuls les modules qui n'importent rien sont testables, donc on extrait de minuscules fonctions pures, et les défauts vivent dans leurs appelants. Les droits des actions serveur sont « testés » par expressions régulières sur le code source (tests/e2e/security.spec.ts:26-47).

Problème. La règle de droits est recopiée 12 fois (celle du paiement 2 fois), et la lecture du formulaire existe en deux copies qui ont déjà divergé : gameEdition et platform n'ont pas la même valeur par défaut, le géocodage n'a lieu qu'à la création.

Solution. Un module tournoi côté serveur. Droits, lecture du formulaire, verrou, liste d'attente et notifications passent derrière une petite interface.

  • Locality : une seule règle de droits
  • Locality : valeurs par défaut posées une fois

  • Tests : verrou et liste d'attente testés par l'interface
  • Corrige : toggleMercenary écrit hors du verrou (1804-1840)
  • Un seul contrat d'erreur au lieu de 3 (null, {error}, {success})
ADR-0004 dit que le code ne change pas de place, et ce chantier en déplace. La friction le justifie (environ 670 lignes de tournoi dans le fichier du forum), mais c'est à trancher.

Problème. Six actions de modération lisent le sujet ou le message par son identifiant, sans le filtre d'accès. Un modérateur peut donc épingler, verrouiller ou modérer dans un forum réservé aux administrateurs. L'écran, lui, réimplémente la règle « fermé / peut modifier » en trois copies divergentes : un bouton s'affiche, puis l'action échoue.

Solution. Un module qui charge l'élément via forumAccess et renvoie ses capacités. Les actions s'en servent pour refuser, la page pour afficher.

  • Locality : une définition de « fermé »
  • Leverage : environ 20 actions + 4 écrans
  • Ferme la faille d'accès des modérateurs
  • Tests de comportement au lieu des expressions régulières

5. Rafraîchissement des pages par concept

Worth exploring in-process
  • app/forum/actions.ts:1039 revalidateTopicLists · topicSplitMergeActions.ts:56 · tournois/actions.ts:89
  • app/page.tsx:48 (home-tournaments) · app/forum/page.tsx:57 (forum-categories)

Problème. On compte 64 appels revalidatePath, chacun avec sa propre liste d'adresses. Le cache home-tournaments n'est vidé que par 2 fichiers : l'annulation ou la création d'un tournoi ne le vide pas, et l'accueil garde l'ancienne version jusqu'à 60 s.

Solution. invalidate.topic(), invalidate.tournament(), invalidate.structure(), appelés par les modules 1 à 3.

  • Locality : un seul endroit sait quelles pages dépendent de quoi
  • Compatible ADR-0005

Recommandation

Commencer par le 2, la politique d'un sujet ou d'un message : c'est le seul candidat qui ferme une faille d'accès, et l'écran retrouve la même règle que le serveur. Le 3 peut le précéder, à titre d'essai : il est petit, isolé et corrige un défaut réel. Le 1, le tournoi, a le meilleur leverage, mais il faut d'abord trancher l'ADR-0004 et poser la seam de test du 4.
