## 3. Ce qui a été fait

### P0 — Sécurité et filet de sécurité (branche `development`)
- **Supprimé deux routes d'API sans protection** qui modifiaient ou supprimaient un utilisateur codé en dur.
- **Les bannis sont bloqués côté serveur** : avant, seul le navigateur les redirigeait, et un banni pouvait encore poster en appelant directement les actions. Les 128 points d'entrée passent maintenant par `getActiveSession()`.
- **Tests automatiques (smoke tests)** : 14 parcours vérifiés à chaque fois (pages publiques, forum, réponse à un sujet, profil, banni redirigé, pas d'email visible, accès par rôle). Ils tournent sur une base de test jetable, jamais sur la tienne.
- **CI GitHub** : à chaque push, vérification automatique des types, du lint, du build et des tests.
- **Mesures de référence** (`docs/baseline.md`) pour comparer les performances avant et après.

### P1 — Organiser le travail de l'IA
- **Kanban** (`kanban/`) : une carte par tâche, son état noté en haut du fichier. `kanban/BOARD.md` est généré automatiquement (`npm run board`).
- **Fiches de décision (ADR)** (`docs/adr/`) : 0001 = le plan de refacto ; 0002 = la stratégie de mise à jour de la base de prod.
- **Conseil de 5 agents** (`/council`) : Factuel, Gardien (avocat du diable), Visionnaire, Avocat des coachs, Modérateur. Testé pour de vrai sur l'ADR-0002.
- **Commandes** `/card` (créer une carte), `/ship` (clôturer une carte avec vérifications).
- **Garde-fous automatiques (hooks)** :
  - l'IA doit demander avant d'ajouter une bibliothèque ;
  - les erreurs de lint lui sont signalées à chaque modification ;
  - un commit est refusé s'il contient `Co-Authored-By`, s'il n'est pas signé breakyt, ou s'il n'a pas de numéro de carte.
- **Skills regroupés** dans `.claude/skills/`, plus un nouveau skill `reuse-first` : l'inventaire de ce qui existe déjà, à consulter avant de créer quoi que ce soit. CLAUDE.md réécrit en version courte, et nouveau `ARCHITECTURE.md`.

### Correctifs de sécurité trouvés en route
- **Emails des membres exposés** : les pages du forum et l'API `/api/articles` envoyaient la fiche complète des auteurs (email, motif de ban, préférences). Désormais, le client de base de données ne renvoie **jamais** l'email, sauf demande explicite pour l'envoi de mails.
- **Catégories réservées visibles par tous les membres** : seuls les visiteurs anonymes étaient filtrés. La recherche ne filtrait rien du tout, même pour les anonymes. Un seul outil (`lib/forumAccess.ts`) applique maintenant la règle « ce rôle et supérieurs » partout : pages, recherche, non-lus, actions.

### P2 — Vitesse du forum (branche `development`)
| Page (connecté) | Avant | Après |
|---|---|---|
| Accueil du forum `/forum` | 16 requêtes | **7** (anonyme : 5 → 0 grâce au cache) |
| Liste d'un forum | 31 | **21** |
| Page d'un sujet | 89 | **46** |
| JavaScript de `/bbscheme` | 235 kB | **183 kB** |

Principales causes trouvées :
- l'ouverture d'un sujet faisait recalculer toute la page une deuxième fois ;
- la barre latérale chargeait des « messages récents » jamais affichés ;
- l'accueil chargeait **tous** les sujets de chaque forum pour n'afficher que le dernier ;
- la session était relue en base plusieurs fois par page.

Le gain se sentira surtout en prod : chaque requête y fait un aller-retour réseau vers Turso.

### Nettoyage (branche `development`)
- Supprimés : 3 fichiers CSS jamais utilisés, la bibliothèque `next-themes` (inutilisée), 4 scripts ponctuels déjà exécutés (dont les 2 qui contenaient le token Turso) et 3 fonctions sans aucun appelant.
- Gardés volontairement : `liste-blessures.md` et `liste-blessures-discord.md`. Ce sont tes fichiers, non suivis par git, et j'ignore leur usage.

### CI : migration oubliée détectée (branche `development`)
Si quelqu'un modifie la structure de la base (`schema.prisma`) sans créer de migration, la CI échoue maintenant tout de suite, au lieu de casser en prod.

### P3 — Monorepo (branche `refacto/p3-monorepo`)
- Le site est déplacé dans `apps/site`. La racine accueillera plus tard `apps/hub` (connexion unique) et `apps/bbscheme`.
- Passage de npm à **pnpm** et **Turborepo**. pnpm, en mode strict, a révélé **3 bibliothèques utilisées sans être déclarées**, que j'ai déclarées.
- Les versions sont figées sur celles d'avant. Sans ça, pnpm aurait pris Prisma 7.10 et une autre version bêta de next-auth : changer d'outil ne doit pas changer le comportement du site.
- Vérifié : types, lint, build et les 14 tests passent.
- **Pour fusionner** : régler d'abord le Root Directory Vercel (section 2, point 5).

### P4 — Essai Tailwind (branche `refacto/p4-spike-tailwind`, partie de la branche monorepo)
- But : prouver que Tailwind v4 (nécessaire pour shadcn) peut arriver **sans rien changer à l'apparence actuelle**.
- Premier essai : ranger tout l'ancien CSS dans une couche. **Rendu modifié** (logo, barre latérale), donc abandonné.
- Solution retenue : seule la règle de remise à zéro `* { padding: 0; margin: 0 }`, celle qui bloquait Tailwind, passe dans une couche.
- Preuve : captures d'écran avant/après **identiques au pixel** sur 3 pages, et une classe Tailwind fonctionne bien.

### Environnement local
Pendant le monorepo, `.env` et `dev.db` ont été déplacés dans `apps/site`. Sur `development` (la branche active maintenant), j'ai remis une copie à la racine et réinstallé les dépendances avec npm, donc `npm run dev` marche comme avant. Pour travailler sur la branche monorepo : `corepack enable` puis `pnpm install`.

## 6. Comment travailler maintenant

1. Une demande → `/card` crée la carte → l'IA présente son plan → tu valides → elle code.
2. Une décision lourde (connexion, base de données, nouvelle bibliothèque, découpage) → `/council`, puis une fiche ADR.
3. Fin de tâche → `/ship` : tests, fiche de la fonctionnalité mise à jour, puis validation de ta part.
4. Les vérifications rapides : `npm run typecheck`, `npm run lint:ratchet`, `npm run test:e2e`, `npm run board`. Sur le monorepo, remplacer `npm run` par `pnpm`.

## 7. Glossaire

| Terme | Explication simple |
|---|---|
| **ADR** (Architecture Decision Record) | Fiche courte qui note une décision technique : le problème, le choix, pourquoi, ce qu'on écarte. Évite de rediscuter la même chose plus tard. |
| **API** | Adresse que le site expose pour donner ou recevoir des données (ex. `/api/articles`). Accessible à quiconque connaît l'adresse. |
| **Backup** | Copie de sauvegarde de la base de données. |
| **Branche (git)** | Version parallèle du code. On travaille dessus sans toucher la version principale, puis on fusionne. |
| **Build** | Préparation du site pour la mise en ligne. S'il échoue, le site ne peut pas être déployé. |
| **Cache** | Résultat gardé en mémoire pour ne pas le recalculer à chaque visite. |
| **CI** (Intégration Continue) | Vérifications lancées automatiquement par GitHub à chaque envoi de code. |
| **Commit** | Enregistrement d'un lot de modifications dans l'historique git. |
| **CSS / couche (`@layer`)** | Le CSS décrit l'apparence. Les couches fixent quelle règle gagne quand deux règles se contredisent. |
| **Dépendance / bibliothèque** | Code écrit par d'autres et utilisé par le site (ex. Prisma, Next.js). |
| **Hook** | Script lancé automatiquement à un moment précis (avant un commit, après une modification par l'IA…). |
| **Kanban** | Tableau de tâches par état : à préciser, prête, en cours, terminée. |
| **LCP** | Temps avant que le plus gros élément de la page s'affiche. Mesure la vitesse perçue. |
| **Lint / ESLint / cliquet** | Le lint repère les erreurs et mauvaises pratiques dans le code. Le cliquet interdit que leur nombre augmente : la dette peut baisser, jamais monter. |
| **Migration (base de données)** | Fichier qui décrit un changement de structure de la base (nouvelle colonne…), appliqué de façon contrôlée. |
| **Monorepo** | Un seul dépôt git qui contient plusieurs applications (site, hub, bbscheme) et du code partagé. |
| **N+1** | Défaut classique : une requête par élément d'une liste au lieu d'une seule pour toute la liste. |
| **npm / pnpm** | Outils qui installent les bibliothèques. pnpm est plus strict : une app ne peut utiliser que ce qu'elle déclare. |
| **OIDC / SSO** | Standard de connexion unique : on se connecte une fois, et on est connecté sur tous les sites liés. |
| **Prisma** | Bibliothèque qui permet au code de parler à la base de données. |
| **Push** | Envoi des commits locaux vers GitHub. |
| **Rebase** | Replacer les commits d'une branche au-dessus de la dernière version d'une autre. |
| **RGPD** | Loi européenne sur la protection des données personnelles (emails, etc.). |
| **Server action** | Fonction exécutée sur le serveur, appelable depuis le navigateur. C'est une porte d'entrée publique, donc il faut vérifier les droits à chaque fois. |
| **shadcn/ui** | Bibliothèque de composants d'interface prêts à l'emploi (boutons, fenêtres…), basée sur Tailwind. |
| **Smoke test** | Test rapide qui vérifie que les parcours essentiels marchent encore. |
| **Spike** | Essai court et limité dans le temps pour vérifier qu'une solution est faisable avant de s'y engager. |
| **Tailwind** | Système de mise en forme par petites classes (`p-4` = marge intérieure de 16 px). |
| **Token** | Mot de passe technique qui donne accès à un service (GitHub, base Turso). S'il fuite, il faut le révoquer. |
| **Turborepo (turbo)** | Outil qui lance les commandes (build, tests) sur toutes les apps du monorepo. |
| **Turso** | Hébergeur de la base de données de prod. |
| **TypeScript / typecheck** | TypeScript ajoute des types au code ; le typecheck vérifie qu'il n'y a pas d'incohérence avant d'exécuter. |
| **Vercel** | Hébergeur du site. Il déploie automatiquement le code poussé sur GitHub. |
